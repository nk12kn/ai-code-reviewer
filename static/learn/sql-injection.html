Understanding & Defeating SQL Injection (SQLi)

An exhaustive engineering guide to how SQL injection vulnerabilities originate, how attackers exploit dynamic string concatenations to manipulate queries, and how to implement airtight parameterized defenses.

What is SQL Injection?

SQL Injection (SQLi) is a classic code-level vulnerability cataloged as CWE-89 and part of the OWASP Top 10 (A03: Injection). It occurs when untrusted user input is directly concatenated, interpolated, or formatted into a database query string before the database engine parses the command.

Because the SQL interpreter cannot distinguish between the developer's intended query control syntax and user-supplied data characters, an attacker can supply characters like single quotes ('), comment operators (--), or logical tautologies (' OR '1'='1) to modify the execution tree of the database query.

The Three Primary Classes of SQL Injection

1. In-Band (Classic) SQLi

The attacker uses the same channel of communication to launch the attack and harvest results. Examples include Error-Based SQLi (extracting schema information via database error messages) and UNION-Based SQLi (appending unauthorized queries using the UNION operator).

2. Inferential (Blind) SQLi

No data is transferred directly in the HTTP response. The attacker reconstructs database records character-by-character by observing server behavior, such as boolean true/false responses or time-based sleep delays (pg_sleep(5)).

3. Out-of-Band (OOB) SQLi

Used when the attacker cannot directly observe response channels and server execution is asynchronous. Triggers DNS lookups or HTTP requests from the database host to attacker-controlled infrastructure.

Vulnerable vs. Secure Implementations

Insecure: String Concatenation & F-Strings in Python

Notice how the query string is evaluated in Python runtime before being handed to the database driver. The database receives already-compromised SQL. 

# HIGH RISK: CWE-89 Vulnerability
import sqlite3

def authenticate(username, password):
    conn = sqlite3.connect("enterprise.db")
    cursor = conn.cursor()
    # Flaw: String formatting combines control logic with untrusted input
    query = f"SELECT user_id, role FROM accounts WHERE user = '{username}' AND password = '{password}'"
    cursor.execute(query)
    # If username is: admin' --
    # Query becomes: SELECT user_id, role FROM accounts WHERE user = 'admin' --' AND password = '...'
    # The password check is commented out completely!
    return cursor.fetchone()

Secure: Parameterized Queries (Prepared Statements)

In parameterized queries, the database engine compiles the query blueprint first. Untrusted parameters are sent separately over the wire as isolated literal data payloads. 

# REMEDIATED: Safe Parameterization
import sqlite3

def authenticate(username, password):
    conn = sqlite3.connect("enterprise.db")
    cursor = conn.cursor()
    # The '?' placeholder instructs the database driver to treat input strictly as a value
    query = "SELECT user_id, role FROM accounts WHERE user = ? AND password = ?"
    cursor.execute(query, (username, password))
    # Even if username contains "admin' --", the DB searches for a user whose literal name is "admin' --"
    return cursor.fetchone()

Can Object-Relational Mappers (ORMs) Have SQLi?

A common myth among engineering teams is that using an ORM (such as SQLAlchemy, Django ORM, Prisma, or Hibernate) completely eliminates SQL injection. While ORMs default to parameterized queries for standard operations like User.objects.filter(id=user_id), SQL injection frequently reappears through:

  • Raw SQL escape hatches: Methods like cursor.execute() or db.session.execute("SELECT ... " + input).
  • Dynamic column sorting: Parameterized placeholders only work for values, not for column names or sorting clauses (ORDER BY {sort_param}). Developers must use strict allowlists for sort keys.
  • Improper ORM extra parameters: In Django, passing untrusted input to extra(where=[...]) allows direct SQL injection.

SQL Injection Remediation Checklist

Mandate Parameterized Queries: Always bind user values using positional (?) or named (:name) parameters.
Employ Static AST Analysis: Use tools like the AI Code Reviewer to catch unparameterized queries before pull requests merge.
Principle of Least Privilege (PoLP): Database users connecting from web apps should never possess DBA or DROP permissions.
Enforce Strict Input Allowlisting: When constructing dynamic table names or sort orders, match inputs against a predefined dictionary of permitted strings.
